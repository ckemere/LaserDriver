# LaserHAT Rev 2 — design notes

Rev 2 does two things:

1. It fixes the Rev 1 problems collected in GitHub issue #3. The display stays an external Adafruit 128×32 OLED bonnet.
2. It splits the board into a **base HAT** and plug-in **output modules**:
   - The HAT keeps the MCU, the BNC I/O, USB-C (power plus UART), the LEDs and the buttons.
   - The laser-diode power stage moves to `LaserDaughter/`.
   - An isolated constant-current estim module will use the same two sockets later.

Everything in this revision is generated by the scripts in `tools/`, starting from the Rev 1 files in git (`a722d88`). See *Rebuilding* below.

---

## Issue #3 and other fixes

| Rev 1 problem | Rev 2 fix |
|---|---|
| Pi UART wired TX→TX, RX→RX | Pi now uses MCU **UART1**: PA8 (TX) → Pi GPIO15 (RXD), PA9 (RX) ← Pi GPIO14 (TXD), on the side of the MCU that faces the header. |
| Pi UART and CH340N shared the MCU's UART0 pins (bus contention once fixed) | CH340N keeps **UART0** (PA10/PA11) to itself. This is also the ROM bootloader UART, so USB-C flashing still works. |
| Display not reachable by the MCU without a Pi | PA0/PA1 (I2C0, 5 V-tolerant open-drain) join Pi GPIO2/3, the bonnet's bus. R19/R20 (4.7 k) are the pull-ups when no Pi is fitted. **JP5** (normally open) feeds the HAT's 3.3 V onto header pins 1/17 so the bonnet runs without a Pi. **Open JP5 before plugging into a Pi.** The bonnet has its own reset chip, so GPIO4 isn't needed. |
| Stim-mirror LED blocked a BNC | BNCs on the bottom edge with a **dual footprint** `Footprints:BNC_Amphenol_031-5540_031-5539_Dual` (built by `tools/make_bnc_fp.py` from the Amphenol drawings):<br>• Placed for the right-angle **031-5540 / 031-5431 / 031-5486**: front face flush with the edge, barrel out.<br>• The Rev 1 vertical **031-5539** fits the same holes (turned 180°); its body then fills the band above, which is kept empty.<br>TRIG IN (J6) is next to the module, STIM OUT (J7) east; bodies are ~0.8 mm apart. The BNC buffer U8 and its parts sit between the MCU and STIM OUT. The BNCs are **DNP**. The 3D view borrows KiCad's B6252HB model. |
| Pi PoE header stopped the HAT sitting lower | Right-edge notch at x 159–165, y 51–59.5 clears the Pi 4 PoE pins and the Pi 5 fan connector. There is no Pi 5 PoE cut-out: on a Pi 5 the HAT sits on a header extender above the cooler anyway. The template's display flex-cable slot on the left edge is removed (no display cable in this system). |
| LEDs far too bright | R13 3 k (PWR), R15 2 k (MCU), R18 2 k (STIM). The 3V3 LED was dropped. The MCU LED is now driven by PA24, so it can show heartbeat or mode. |
| RGB 5 V/12 V indicator; wish for an internal measurement | Moved to the laser module as a divider (R1/R2) into **ADC_B**. The OLED/web GUI shows the measured compliance rail. The RGB LED, zener and two resistors are gone. |
| USB-C VBUS tied straight to the Pi 5 V rail | PFET ideal diode: Q3 **AP30P30Q** (PDFN3333, 13 mΩ max; ~0.12 W at 3 A) plus Q4 DMMT5401 matched-PNP control, the circuit from the Pi HAT back-powering guidance. It blocks back-feed into the USB host when the Pi has its own supply. The power path J5 → Q5 → Q3 → header 5 V pins is hand-routed (0.6–0.8 mm). |
| No way to cut power without unplugging | **USB power switch.** SW10 (SHOU HAN MSK12C02 right-angle slide) sits on the left edge under MH1, with the USB-C connector moved down below it; lever toward the header = ON. SW10 drives the gate of Q5 (**AP30P30Q**, PDFN3333 P-FET, 13 mΩ max), which sits in series with VBUS ahead of the ideal diode. R26 100 k holds Q5 off when the switch is open. It cuts only the HAT's USB-C input: a Pi on its own supply stays up. |
| BNC trigger input straight into a non-5 V-tolerant MCU pin; mirror output driven straight from the MCU | U8 74LVC2G17 dual Schmitt buffer (5 V-tolerant inputs). Input: 1 k series + 100 k pull-down. Output: 33 Ω series; the STIM LED follows the buffered output. |
| CH340N V3 pin only had a cap (wrong at 3.3 V) | V3 tied to VCC per the datasheet; C5 removed. |
| MCU exposed pad (pin 33) unconnected | Tied to GND with a 2×2 via-in-pad array. |
| Pi→MCU trigger shared the SWD data pin | Dedicated line: Pi GPIO26 → **PA27** (TIMG7_CCP1 / TIMG8_CCP1 capture). SWD stays on GPIO24/25, swapped: GPIO24 → SWCLK, GPIO25 → SWDIO. |
| UI buttons (SW1–SW4, top-press) would be buried under the output module | Edge-operated controls, reachable with the bonnet and a module fitted:<br>• **SW7**: SHOUHAN BL-DT side thumbwheel (LCSC C53223909) on the left edge, y 81–93.5, wheel ~6 mm past the edge. Roll = up/down, push = select. ## MSPM0G3507 (VQFN-32) pin map

The pin map was re-chosen to untangle the MCU fan-out (`tools/pinopt/opt.py` in the scratch history; the method is described below the table). U7 is turned 270° and sits at (134, 71). Each side of the chip faces its destinations:

| Side | Faces | Pins |
|---|---|---|
| North | header | I2C, NRST, power, ROSC |
| West | J8/J9 and the buttons | UART0, PWM, buttons |
| South | — | DAC, ADC_A, BSL, SWD |
| East | BNC buffer, LEDs, FIRE | STIM_OUT, LED, FIRE, Pi UART, DB_GPIO, VCORE |

| Pin | Port | Net | Use |
|---|---|---|---|
| 1, 2 | PA0, PA1 | I2C_SDA, I2C_SCL | I2C0 → Pi GPIO2/3 (OLED bonnet, stand-alone mode) |
| 3 | NRST | GPIO23 | reset (Pi GPIO23 — **swapped with MCU_POWER_EN vs Rev 1**, now GPIO18; CH340 RTS via JP4) |
| 6 | PA2 | ROSC | 100 k 0.1 % |
| 7, 8, 9 | PA3, PA4, PA5 | — | spare (no-connect) |
| 10 | PA6 | DB_GPIO | module GPIO; **TIMA0_FAULT0** for the hardware PWM kill |
| 11 | PA7 | DB_PWM_A | **TIMA0_CCP1** → module (J8.3, EN) |
| 12, 13 | PA8, PA9 | PI_RXD, PI_TXD | **UART1** TX/RX ↔ Pi GPIO15/14 |
| 14, 15 | PA10, PA11 | MCU_UART_TX/RX | UART0 ↔ CH340N (and BSL) |
| 16 | PA12 | DB_PWM_B | **TIMA0_CCP3** → module (J8.4, CATH) |
| 17 | PA13 | BUTTON4 | thumbwheel SW7 roll |
| 18 | PA14 | BUTTON2 | thumbwheel SW7 push = select |
| 19 | PA15 | DB_DAC | DAC0 → module (laser setpoint; e-stim CS_n) |
| 20 | PA16 | BUTTON3 | thumbwheel SW7 roll |
| 21 | PA17 | DB_ADC_A | ADC1.2 ← module (laser photodiode; e-stim SCK) |
| 22 | PA18 | BSL_INVOKE | BSL button SW6 |
| 23, 24 | PA19, PA20 | SWDIO, SWCLK | ← Pi GPIO25 / GPIO24 (**swapped vs Rev 1** so the traces don't cross) |
| 25 | PA21 | BUTTON1 | BACK button SW8 |
| 26 | PA22 | DB_ADC_B | ADC1.8 ← module (laser compliance rail; e-stim MOSI) |
| 27 | PA23 | BUTTON5 | FIRE button SW9 |
| 28 | PA24 | LED_MCU | status LED D7 |
| 29 | PA25 | MCU_STIM_OUT | → U8 → BNC STIM OUT (J7) + STIM LED; TIMG12_CCP1 |
| 30 | PA26 | MCU_STIM_IN | ← U8 ← BNC TRIGGER IN (J6); TIMG8_CCP0 / TIMG7_CCP0 capture |
| 31 | PA27 | PI_TRIGGER | ← Pi GPIO26; TIMG7_CCP1 / TIMG8_CCP1 capture |

**How the map was chosen.** The fixed functions stay put:
- I2C0 on PA0/PA1;
- NRST;
- ROSC (PA2);
- UART0/BSL (PA10/PA11);
- DAC (PA15);
- BSL_INVOKE (PA18);
- SWD (PA19/PA20).

Every other function was allowed on any pin that supports it (per SysConfig's pin-mux data). A search over the four MCU rotations and a grid of positions then minimised the number of pin-to-destination paths that cross on the top layer. Pi-header nets need a via anyway (J1 is a bottom-side part), so they were allowed to cross. The old map had ~44 such crossings; the new one has ~5.

## Daughterboard (output module) interface

There are two 1×5 2.54 mm sockets on the HAT. They sit in an L shape, which also keys the module. Male pins go on the module's underside.

| | Pin 1 | Pin 2 | Pin 3 | Pin 4 | Pin 5 |
|---|---|---|---|---|---|
| **J8** (row, pin 1 at x 109.0, y 78.5, +x) | GND | +5V | PWM_A (PA7) | PWM_B (PA12) | GPIO (PA6) |
| **J9** (column, pin 1 at x 125.5, y 82.0, +y) | GND | +3V3 (switched MCU rail) | DAC (PA15) | ADC_A (PA17) | ADC_B (PA22) |

- **Why GND is on pin 1:** GND sits on the end pin of each socket so the ground pour can always reach it.
- **Module outline:** 26.5 × 23.5 mm, x 101–127.5, y 76–99.5 in HAT coordinates.
- **Keep-out on the HAT:** a footprint keep-out (rule area `DAUGHTERBOARD`) covers the middle of that area. Buttons SW1–SW4 stay under the module's edges; they're side-actuated, so they can still be pressed.
- **Module power:** each module brings its own supply stage (laser: 5 V→12 V boost; estim: isolated DC-DC). The HAT provides only +5 V and the MCU's switched 3.3 V.

## Laser module (`LaserDaughter/`)

This is the Rev 1 laser sheet with the following changes:

- Its inputs come from the headers. J1 and J3 are male headers matching HAT J8 and J9.
- **Designed for 300 mA** (the red LD's maximum is 280 mA):
  - Rs1 = 2 Ω 1 % 1206 (0.18 W at 300 mA).
  - The DAC setpoint is divided by R3/R4 (39 k / 10 k) into IREF, so I = V_DAC × 10/49 / 2 Ω ≈ 102 mA/V. Full scale (3.3 V) ≈ 337 mA; 300 mA ≈ DAC code 3650. **Firmware/GUI current scaling changes accordingly.**
  - C11 filters IREF.
- **Q2 = NDT3055L** (SOT-223, logic level, V_GS ±20 V, in stock). It sits on the top side with open pads so a different MOSFET for a blue LD can be swapped in by hand.
- **U3 (op-amp) runs from +5 V instead of LASER_V**, with its own 100 nF bypass C12.
- Boost converter:
  - L1 = 10 µH, I_sat ≥ 1.5 A (Bourns SRN4018-100M).
  - D3 (and D1) = DSK14, a 1 A / 40 V Schottky (SOD-123FL). SS14FL is out of stock.
  - The C8 → L1 → U2 → D1 → C9 loop is kept to a few mm.
- **Dummy-load fix.** Rev 1 drew the dummy-load zener forward-biased. The stack is now LASER_V → D3 → D2 (2.4 V) → D4 (2.7 V) → Q1. **J5 "RED" (2-pin 2.00 mm shunt) shorts D4** for the red diode. D2/D4 are ROHM KDZVTR2.4B / KDZVTR2.7B (1 W, SOD-123FL); 1 W zeners this low aren't stocked in SMA.
- J4 (PD cathode configuration) is now a solder jumper.
- R1/R2 (100 k / 33 k) scale LASER_V into ADC_B: 12 V → 2.98 V, 5 V → 1.24 V.
- The 5 V/12 V slide switch SW5 overhangs the module's left edge.

**Layout.** Parts are grouped by function:

| Block | Parts / location |
|---|---|
| Boost | top-left |
| LD socket | left-middle |
| Current sink | bottom-right: Q1 → Q2 → Rs1, with U3/R3/R4/C11 beside it |
| Dummy-load stack | centre |
| PD load and compliance divider | next to J9 |

Routing is on F.Cu with a near-solid GND plane on B.Cu:

- Power nets are 0.8–1.0 mm and laser-current nets 0.5–0.6 mm.
- U3's current sense (IN−) is a separate thin Kelvin trace to Rs1's pad.

The router (`tools/grid_router.py`, plan in `LaserDaughter/route_plan.json`) is a two-layer A* router:

- 0.1 mm grid, 45° steps.
- Nets are grown as trees, necked down onto small pads.
- Thin supply branches (`pad_widths`) are routed last.
- Nets that fail are ripped up and promoted.

**Thermal check for blue LDs.** Q2 dissipates (LASER_V − V_LD − V_Rs1) × I. At 12 V with a ~5 V blue diode that is ~2 W at 300 mA.

- **Continuous operation** would be too much for a SOT-223 on this board.
- **Typical use:** 100 ms pulses at ≤ 1 Hz, which is ≤ 10 % duty.
  - Average dissipation is ≤ 0.2 W.
  - A single 100 ms pulse sees the SOT-223's transient thermal impedance, roughly 20–30 K/W, instead of its ~80 K/W steady-state value. The junction swings a few tens of °C per pulse, which is well within limits.
  - The pulse is also inside the NDT3055L's safe operating area.

So a blue diode at full current is fine for this protocol. Revisit Q2's heat-sinking (larger copper or a TO-252 part) only if long or continuous exposures are needed.

## E-stim module (`EStimDaughter/`)

This is the isolated biphasic constant-current stimulator (rev M3). It was designed in a separate session against `estim_interface/ESTIM_MODULE_SPEC.md` and imported from `kbest/estim_module` at kbest commit `9200766`. The project was renamed `estim_module` → `EStimDaughter`, and the script paths and schematic instance names were updated to match. `EStimDaughter/README.md` is the full description; `DESIGN_NOTES.md` covers its history.

**Circuit summary**
- **Control.** A digital-only barrier: an ISO7761F carries EN, CATH, CS_n, SCK and MOSI across, and FAULT_n back.
- **Set-point.** An MCP4921 DAC with a TL431-derived 1.000 V reference produces +VSET. An OPA2192 inverter makes −VSET.
- **Waveform.** A 74HC4053 selects ±VSET (CATH) or 0 (EN) into a floating-load V→I stage: I = V / 2.00 kΩ, 0–500 µA.
- **Electrode path.** The electrode is behind a 1 µF DC block. A DG419 shorts it ~200 µs after each pulse pair.
- **Fault detector (M2, 2026-09-28).** An LM393 window on the electrode-side voltage (trip at |E1| > 0.915 × rail) pulls FAULT_n low a few µs before the output stage runs out of compliance, or within ~4 µs of EN on an open electrode; the HAT's latched TIMA0_FAULT0 then kills EN/CATH. Same line still reads low while the isolated side is unpowered. See `EStimDaughter/DESIGN_NOTES.md` and HAT NOTICE 11.
- **Power.** The isolated ±15 V comes from a DNP SIP DC-DC (or battery packs).
- **Board (M3, 2026-09-28).** 26.5 × 36.5 mm — the module extends 12.5 mm past the HAT's south edge over the Pi's port edge (NOTICE 12; the HAT's keep-out marker still needs extending to y 112.5). 4 layers, all parts on the top (single-sided assembly), 2 mm isolation gap. On the original 23.5 mm outline the fault-detector version would not route; see `SMA_VS_BNC_STUDY.md` for the options that were considered.

**Import checks (2026-09-26)**
- ERC: 0 violations. DRC: 0 errors, 0 unconnected.
- Schematic-parity warnings, all present in the original:
  - footprint library prefixes;
  - "/"-prefixed local net names.

  They are resolved by one "Update PCB from Schematic".
- J8/J9 pads land exactly on the HAT sockets, with matching pin functions. The HAT drives PA15/17/22, PA7/PA12 and PA6 directly, with no filtering.
- The `sim/` scripts reproduce the documented quick-mode results from the new location:
  - phase margin 70.7° (no cable) and 48.4° (470 pF);
  - set-point −0.35 %;
  - 221 µs / 21.5 µs maximum phase width at 100 / 500 µA;
  - SHORT keeps the electrode reset.

**Open items**
- ~~Electrode header vs. BACK button~~ — resolved in M3: J1 is on the module's new south edge at y ≈ 111, 12.5 mm beyond the HAT and the BACK button.
- **The module's own open items:** enclosure clearance for the 12.5 mm overhang and J1, cable capacitance, U5A DC drift for fast trains, PS1 sourcing.

## Impact on firmware and Pi software

- Pi link: **UART1** on PA8 (TX) / PA9 (RX) (was UART0; earlier Rev 2 drafts used UART2, then UART3). CH340N: UART0 on PA10/PA11.
- Pi trigger: GPIO26 → PA27. `brokerd`/`pi_trigger.py`/`web_app.py` currently use GPIO24 → PA19 (Rev 1). **That path is gone on Rev 2**: GPIO24 now lands on SWCLK (PA20). Move them to GPIO26.
- Pi header wiring changes vs Rev 1: SWD swapped (GPIO24 → SWCLK, GPIO25 → SWDIO), and NRST / MCU power enable swapped (GPIO23 → NRST, GPIO18 → MCU_POWER_EN). Flash a Rev 2 board with `make flash HAT_REV=2` (add `OPENOCD_GPIOCHIP=4` on a Pi 5). That sets the OpenOCD pins and passes the power/reset pins to `Pi/power_cycle.py` (`LASERHAT_POWER_PIN` / `LASERHAT_NRST_PIN`). The defaults stay Rev 1.
- New inputs and outputs: I2C0 on PA0/PA1 (stand-alone OLED), LED on PA24, ADC_B on PA22, DB_GPIO on PA6. BNC stim out/in moved to PA25/PA26.
- BNC paths are non-inverting through U8, so the polarity is unchanged.
- Buttons: BUTTON1 = BACK, BUTTON2 = select (wheel push), BUTTON3/4 = wheel roll, and the new BUTTON5 = FIRE; the button pins are now BUTTON1 PA21, BUTTON2 PA14, BUTTON3 PA16, BUTTON4 PA13, BUTTON5 PA23. **BUTTON1–5 are now active LOW**: their commons go to GND, so enable the internal pull-ups (not pull-downs) and invert the read. This keeps MSPM0_3V3 off the board edges. SW6 (BSL, PA18) stays active high, because the ROM samples PA18 high at reset. The Pi GUI's button map (`Pi/README.md`, "buttons") changes accordingly: roll = decrement/increment, push = select/cycle parameter, BACK = back, FIRE = trigger a pulse.

### Firmware requirements agreed with the e-stim module (see `estim_interface/QUESTIONS.md`)

- **Pins:** PA15 (CS_n), PA22 (MOSI) and PA17 (SCK) become push-pull GPIO for bit-banged, write-only 16-bit SPI (mode 0) to the module's isolated MCP4921. CS_n idles high. Transfers happen only between trains.
- **Pulse outputs:** PA7 = TIMA0_CCP1 (EN) and PA12 = TIMA0_CCP3 (CATH, *not* CCP0_CMPL). They are independent edges: CATH leads EN by ≥ 5 µs and changes only while EN is low. EN edge precision is ~0.1 µs.
- **Fault:** PA6 = TIMA0_FAULT0 (was PA26, also FAULT0), active-low, latched, forcing both CCP1 (EN) and CCP3 (CATH) low. It is armed only after FAULT_n reads high at start-up (module isolated supply up; ~100 ms timeout means "module not ready"), and cleared only between trains. Faults are reported to the Pi.

## Rebuilding

```sh
python tools/rev2_migrate.py                # HAT schematics (kiutils)
python tools/make_laser_daughter.py         # laser module schematic
sh tools/build_hat_pcb.sh --route           # HAT PCB (~20 min) - DO NOT run on the hand-routed LaserDriver.kicad_pcb
sh tools/build_daughter_pcb.sh --route      # laser module PCB (a few min)
$KICAD_PY tools/jlc_fab.py                  # JLC Gerbers/BOM/CPL/renders -> fab/ (see fab/README.md)
# e-stim module: EStimDaughter/gen_schematic.py, tools/netcheck.py, then tools/route_pcb.py (see its DESIGN_NOTES.md)
```

On macOS the scripts were run with the `kicad` micromamba env (kiutils) and KiCad's bundled Python for `pcbnew`; on
Ubuntu (2026-09-28 onwards) one venv with the system `pcbnew` does both, `kicad-cli` is on PATH, and the e-stim tools
take `FREEROUTING` / `KICAD_CLI` / `KICAD_FOOTPRINTS` from the environment. The `/Applications/...` paths in the HAT
tools (`build_*_pcb.sh`, `jlc_fab.py`, `silk_declutter.py`, `pcb_sync.py`, `schlib.py`) are still the macOS ones.

The PCB flow runs in this order:

1. `pcb_sync` (headless "update PCB from schematic"; keeps footprint UUID paths)
2. `hat_layout` / `daughter_layout` (placement, outline, keep-outs, silkscreen)
3. `hat_preroute` (hand-routed 5 V power path)
4. `gnd_vias` (a via beside every SMD ground pad)
5. freerouting (best of N attempts)
6. `stitch` (ground stitching vias)
7. `fix_islands` and `maze_route` (whatever is left)
8. `silk_tidy` (reference designators placed clear of pads and other silk, or hidden)

The HAT uses steps 5–7. Freerouting varies from run to run and tends to leave small ground islands behind. `hat_preroute` pre-routes the spots that were boxed in:
- the USB-C VBUS → Q5 → Q3 → +5 V power chain;
- R8/R10 ground;
- J5's two GND pin pairs, tied to the shield pads;
- J1 pin 25's via;
- U5's ground via;
- C12 → U4 ground.

The auto-routed board is saved in `stash/LaserDriver_autorouted_2026-09-27.kicad_pcb`; `LaserDriver.kicad_pcb` itself was rebuilt without `--route` for manual routing. The saved board (USB-C/switch swap, MCU pin map optimised, U7 at (134, 71) rot 270) needed three hand fixes after the route. A fresh `--route` build won't repeat them:
- **DB_GPIO:** moved from PA27 (pin 31, east side) to PA6 (pin 10, west side), then maze-routed. The route is short, with 2 vias.
- **PI_RXD:** its B.Cu run was moved to hug /GPIO25 (x 136.82). The old run fenced off a B.Cu ground sliver that stranded C3's ground via.
- **U8:** pin 2 got a ground via from `island_via.py`.

Result: 61 signal vias, down from 73 before the pin-map optimisation. DRC shows 0 unconnected and 0 parity issues.

After any fresh `--route` build, check DRC, `tools/netcheck.py` and `tools/gnd_islands.py`. `tools/island_via.py` can tie a leftover ground island with one via when there's room.

On the module, steps 3 and 5–7 are replaced by `grid_router`.

**Note:** `generate_schematics.py`, `fix_labels.py` and `merge_template.py` predate the hand-edited Rev 1 schematics. Running them would overwrite that work.
